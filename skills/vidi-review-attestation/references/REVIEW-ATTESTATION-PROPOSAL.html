deep-review → vidi: the review-attestation seam

How the deep-review CLI reports "reviewed-clean" back to vidi — part 2 of the attestation matrix.

DESIGN RECOMMENDATION · opus synthesis of a gpt-5.5 review cohort (vid codebase · git-ai · ~110 vidi transcripts) + adversary · 2026-07-07

verdict Buildable on deep-review's side; blocked on two vidi-core changes that aren't deep-review's to make.

vidi already has the record, ledger, gate, and the ToolReviewV2 predicate — this is not a from-scratch build. deep-review emits one unsigned ToolReviewV2 statement per reviewed unit through vidi review (never vouch/sign). But it cannot do so today: ReviewArgs has no non-interactive flags (blocking prerequisite), and anything above the self-asserted A0 floor needs a Lane::Tool that does not yet exist (roadmap). Recommend a phased path: honest A0 transparency-floor now → signed tool lane later.

1 · What's actually there (dispelling "stubbed")

Only vidi-cli's verbs are println! stubs. vidi-core is real and load-bearing:

  • Record model — Predicate::Review + AttesterIdentity::Tool{tool,model,…} already mints PredicateType::ToolReviewV2 at Statement::new. No new predicate needed.
  • Units are content-addressed — Address = path::qualpath; scan_file → Unit{address, content_hash, line_span, grade}. content_hash is blake3 over an alpha-normalized atom sequence (normalize.rs).
  • Staleness is automatic + pure — staleness::resolve_gate_state is exact-hash equality vs the reviewed hash. Any byte change → STALE. No churn formula involved.
  • Normative boundary — ratified pin agent-sign-boundary (D2/D8, 2026-07-03): "Agents cannot sign; signing requires a human." The presence-gate wall below is by design, not incidental.

2 · The design

Data shape — reuse ToolReviewV2, add nothing

Per reviewed unit, one statement:

subject   : { name: Address(path::qualpath), digest: <resolved by vidi, NOT by deep-review> }
predicate : { attesterIdentity: Tool{ tool:"deep-review", model:<"gpt-5.5"|"claude-opus-4-8"|…>, harness:"claude-code" },
              criteria, rigor, verdict, claimTimestamp,
              similarityMultiset, profileVersion, scopeModelVersion, invarianceGrade }
              // NO authorship field — composition is a read-time join (§Matrix), never embedded payload

Unit mapping — deep-review's glue

No diff-to-unit API exists anywhere in vidi (confirmed independently by two reviewers). deep-review maps its frozen-worktree diff hunks → units by intersecting changed line-ranges against each post-image line_span from scan_file. This glue is deep-review's to write.

single-verifier constraint deep-review must never compute a unit's blake3 itself and pass it as --digest — that would be a second hasher outside normalize.rs, violating the ratified "exactly one canonicalize/content_id/verify reachable from every consumer" pin. deep-review supplies identity + verdict + rigor by address; vidi review resolves and hashes the current unit content itself.

honesty — do not oversell The A0 line is an honor-system convention, not a control. The "same F1 floor everyone reads" framing is a rationalization: that floor was never cryptographic — it was bounded by a human's willingness to lie under a registered Person{id} (checked against [reviewers]). At A0, ledger::append() checks only that .vidi/ exists (zero identity/auth), Tool{tool,model} is free text with no registry check (anyone can claim model:"claude-opus-4-8"), and .gitattributes merge=union makes a hand-crafted line survive merges by default. Auto-minting also removes the friction that implicitly bounded the floor, on two axes: volume (thousands of lines/hr → craters signal-to-noise) and attribution (no tool identity is verified). So the writeup must say plainly: this is transparency-by-plain-file, not integrity. Real integrity arrives only with the tool lane below.

Invariants deep-review owns (these are the whole point)

  • hard gateNever mint from a degraded reviewer. vidi has no "degraded" concept — Verdict is Approved|Rejected. The workflow already tracks status[r.key] = 'ok' | 'degraded:…'; the mint gate must check that per-reviewer status directly, not "is the confirmed list empty" (a crashed reviewer reports zero findings — which must never read as clean). Needs an explicit test: no mint call reachable when degraded=true.
  • hard gateDerive rigor from observed scope. Mint only when the reviewer's actual diff scope covered the full unit body — a reviewer that saw one hunk of a function must not attest the whole unit's hash. Never let the wrapper self-assert rigor.
  • dedupPre-mint check: skip re-appending an identical already-approved line (unbounded ledger growth on re-runs). Harmless to gating, but wasteful.

Rename handling — fail closed, don't oversell invarianceGrade:code

Because content_hash is alpha-normalized, renaming a unit's own name/params doesn't change its hash — but Address embeds the literal name, so a rename is a new address with no review history → reads UNREVIEWED until an opt-in, never-automatic reconcile_offer (16-atom floor + exact-hash match at the new address) is surfaced and accepted. deep-review must not advertise code-grade as "silently survives a rename" — it fails closed by design. Either skip minting on renamed units or explicitly surface the reconcile path.

Matrix composition — a read-time join, never a stored field

Two incompatible invalidation clocks. vidi's review key is content-hash — commit-independent, staying FRESH across many later commits. git-ai's authorship key is commit+file+line-range — it rotates on essentially every commit that touches the file. An authorship reference frozen into a review record therefore goes stale the commit after mint, while the review itself is still validly fresh; embedding it would splice the two clocks and corrupt the record by design. There's no schema slot for it anyway — ReviewPredicate has no authorship field, and D2's authorship pin is explicitly "code-free, current-state, advisory-only" (re-resolve on demand, never carry as payload). Nor is there a stable per-commit git-ai artifact to freeze correctly: resolving "who wrote this" is blame-style backward-walking, inherently a query-time operation.

So compose at read time. A report/query command — not the mint path — resolves a unit's current line_span against git-ai's current blame/note at HEAD, independent of when the ToolReviewV2 line was minted. The matrix row ("who wrote U × who reviewed U clean") is computed on demand, never stored. And don't mirror a refs/notes/review channel: authorship is advisory (a git-note side channel is fine), but review must gate — it needs vidi's ledger-lane + policy axis, which git-notes has no equivalent of.

availability gap git-ai migrates authorship across rebases via a post-rewrite hook — but only where git-ai install-hooks registered it. In a CI runner or fresh clone without hooks, a rebased/amended commit gets no note at all (absent, not stale), with no backfill path — precisely the environments where vidi's gate runs. So the read-time join must detect-and-flag missing authorship, never assume-stale, and vidi-gate environments should ensure git-ai hooks are installed. A deployment gap, not a flaw in git-ai's rewrite tracking (correct when hooks are present).

4 · Corrections to the original brief

  • No "significance × churn" gate exists or was proposed. Significance and severity are both advisory, feeding only vidi queue ordering (D2). Drop that framing.
  • This is first-cut design. The "part-1 solved / part-2 unsolved" split originates in this session's brief, not prior ratified art — so treat the above as a proposal to ratify, not a synthesis of settled decisions.

5 · Recommended next step

Land the A0 phase: (1) give vidi review the non-interactive flag contract above; (2) build deep-review's diff→unit mapper + the three mint invariants (degraded/coverage/dedup) with the degraded test; (3) label every emitted line honestly as A0/self-asserted. Defer Lane::Tool signing to the vid roadmap. That ships a working, honest review-attestation seam without overstating its cryptographic strength.
